## Deploy kit architecture

All scripts `source bin/common.sh [<app>]`, which loads `conf/atms.env` (global) and, if an app name is given, `conf/apps/<app>.env` (per-app). **The file name is the app identity**: `<app>` = container name = image `localhost/<app>` = `logs/<app>/` = `config/<app>/` = Quadlet unit `<app>.service`. Adding a module = adding `conf/apps/<module>.env.example` + `<module>.container.env.example`, then `bin/init-dirs.sh` (copies `*.example` → real files without overwriting).

Two env files per app, intentionally separate:
- `conf/apps/<app>.env` — sourced by bash (ports, CPU/MEM, health path).
- `conf/apps/<app>.container.env` — passed to `podman --env-file` (Spring profile, `JAVA_OPTS`). Podman env-file format (no quotes, values may contain spaces), so `bin/direct.sh` parses it line by line instead of `source`-ing it. Keep values unquoted.

Image lifecycle (`bin/deploy.sh <app> <jar>`): `build.sh` tags `localhost/<app>:<yyyyMMdd-HHmmss>` (prints the tag as its last stdout line; logs go to stderr) → old `:current` retagged `:previous` → new tag becomes `:current` → stop/start → `healthcheck.sh` (2xx/3xx on `HEALTH_PATH`) → on failure `rollback.sh <app> previous`. Containers always run `:current`; rollback is just retagging.

Run modes are switched implicitly:
- If `~/.config/containers/systemd/<app>.container` (Quadlet) exists, `start.sh`/`stop.sh` go through `systemctl --user`; otherwise plain `podman run --restart=unless-stopped`. Quadlet requires linger (infra request).
- `bin/direct.sh start|stop|status <app> [jar]` is the **no-container fallback** (runs `~/atms/jdk/bin/java -jar` with a pid file) used until a Java base image is carried in. It reuses the same config/log dirs so switching to containers needs no config change.

Dockerfiles in `deploy/` take a **prebuilt** `app.jar` (build context `~/atms/build/<app>/`). `Dockerfile` expects a JRE base image (`BASE_IMAGE` in `conf/atms.env`); `Dockerfile.jdk-local` puts the uploaded `~/atms/jdk` onto an OS-only base image. The containers run as in-container root on purpose: with rootless Podman that maps to the work account (`atmswas`) on the host, so mounted `logs/`/`config/` stay writable/deletable by the user.

`deploy/jenkins/` is the bank variant of `NH-ATMS/infra/jenkins` (no GitLab/GitHub/Slack, adds Gitea plugin, bakes docker CLI + compose plugin + Node 22, 1 executor). It must be **built on an internet-connected PC** — plugins can't be installed on the closed network. ## Commands

No build/test tooling exists for the kit itself; validate scripts with:

```bash
bash -n bin/*.sh          # syntax check
```

The scripts call `podman`, `curl`, `systemctl --user`; to exercise logic off-server, put stub `podman`/`curl` executables first on `PATH` and point `BASE_DIR` (in `conf/atms.env`) at a temp dir.

On the server (from `~/atms`):

```bash
bin/init-dirs.sh                          # first time: create conf/*.env, logs/config dirs
bin/precheck.sh                           # read-only environment check (no sudo)
bin/load-image.sh images/<image>.tar.gz   # podman load
bin/deploy.sh atms-web release/<jar>      # build + start + health check (+ auto rollback)
bin/status.sh [<app>]  |  bin/logs.sh <app> [file]  |  bin/rollback.sh <app> [tag]
bin/install-quadlet.sh <app>              # auto-start via systemd --user (needs linger)
bin/direct.sh start <app> <jar>           # fallback without containers
```

For NH-ATMS build/test/run commands see `NH-ATMS/CLAUDE.md`.

Building NH-ATMS anywhere offline: the root `build.gradle` pins the toolchain to **Java 21, vendor Eclipse Temurin**, and foojay auto-download can't work without internet. With only Oracle/Red Hat JDKs present the build fails with "Cannot find a Java installation ... vendor=Eclipse Temurin"; point Gradle at a local Temurin with `-Porg.gradle.java.installations.paths=<temurin-21-dir>` (plus `-Porg.gradle.java.installations.auto-download=false`).

## Repository conventions

- `.gitattributes` forces LF for `*.sh`, env and yml files: files reach the server from Windows via SFTP and CRLF breaks bash. Guides also tell users to run `sed -i 's/\r$//' bin/*.sh`.
- Root `.gitignore` deploy-kit entries are **anchored to the root** (`/config/`, `/logs/`, `/images/`, ...). Unanchored patterns previously would have excluded same-named directories inside `NH-ATMS/` (e.g. Spring `config` packages). Keep new kit-runtime ignores anchored.
- GitHub rejects files > 100 MB; `.gitignore` excludes `*.exe`, `**/publish/`, jars (except `gradle-wrapper.jar`), archives, `.env`.
