## 0. 핵심 전제 (3-시스템 경계)

NH AS-IS는 **AP / ATMS / AJMS** 세 시스템으로 구성된다. TO-BE 처리 방향:

| AS-IS 시스템 | 정체 | TO-BE 처리 |
|---|---|---|
| **AP** | 계정계 ATM 거래처리 앱 (거래·원장·정산) | **계정계팀 이관** — 단, 일부 화면/데이터는 ATMS가 *조회용*으로 가져옴 (본 문서가 선별) |
| **ATMS** | 기기·장애·시재·원격 관리 시스템 | **우리 핵심 범위** (정본 = `ATMS Table 1.pdf` 588건) |
| **AJMS** | ATM 저널관리 시스템 | **우리 `atms-journal` 모듈로 대체** |

> ✅ **농협 공식 확인 (2026-06-01 사전 기술협상 #2)**: "자동화기기 관리시스템은 코어뱅킹에 포함되어 **ATMS와는 완전 분리** 예정". 본 문서의 AP=계정계 이관 전제가 발주처 확인됨.

### 🔑 가장 중요한 결정 원칙
> **AJMS를 우리가 대체하므로, 우리는 이미 거래저널(Transaction 71) 원천을 보유한다.**
> 따라서 AP의 거래조회 화면은 **"이관"이 아니라 "우리 저널 데이터로 재구현"**한다.
> AP 화면은 *업무요건 참고용*이지 데이터 소스가 아니다.

**소유권 경계선 (단일 기준):**
- **기기/운영 관점**(시재검증·마감대사·장애연계) → **ATMS 소유**
- **계정 원장 관점**(정정·원장반영·정산) → **계정계(AP) 소유**

## 2. AP에서 실제로 "받아야" 하는 데이터 의존성

화면이 아니라 **데이터 연동**으로 정리한다. (이게 PM이 계정계와 협의할 실제 목록)

| # | 데이터 | 용도 | 연동 방식 | 소유 |
|---|---|---|---|---|
| D1 | 거래저널(71) | 거래내역조회 전체 | **우리 저널 DB** (이관 불요) | ATMS |
| D2 | 계좌·고객 **명칭** | 거래조회 시 고객명 표시 | **계정계 조회 API** | 계정계 |
| D3 | 마감 집계/합계 | 집계내역·전자결재 | 기기 마감전문 + 우리 집계 | ATMS |
| D4 | 2차파기 보관 데이터 | 감독규정 조회 | 파기보관소 + 승인 | ATMS+감사 |
| D5 | 거래 정산/원장 대사 | 정산 | **계정계 소유** (연동만) | 계정계 |
| D6 | ILM_ 거래통계 | 보고서 요약통계 | 요약만 ATMS, 정밀은 계정계 | 분담 |

**결론:** AP에서 *데이터 이관*이 필요한 건 사실상 없고, **계정계 조회 API(D2)와 정산 연동(D5)** 두 접점만 협의하면 된다. 거래조회의 본체 데이터(D1)는 이미 우리 저널에 있다.

---

## 3. 저널(AJMS 대체)로 커버되는 범위 — 명확화

- 우리 `atms-journal` = `T_TRANSACTIONJOURNAL` 보유 → **거래내역조회(1000~1008)는 100% 자체 제공 가능.**
- 즉 NH가 거래조회를 위해 AP에 의존하던 구조가, TO-BE에서는 **저널 단일 소스**로 단순화된다.
- 남는 의존: 고객 **명칭** 조인(D2)만 계정계 API. 거래 *내용*은 저널에 다 있음.

## 4. 계정계 협의 체크리스트 (PM용)

- [ ] **D2 계정계 조회 API**: 계좌→고객명/생년월일 조회 인터페이스 스펙·권한·개인정보 마스킹 규칙

## 6. 한 줄 요약

> **AP는 계정계로 가고, AP의 거래조회 화면은 우리 저널로 재구현한다.**
> ATMS가 AP에서 진짜 가져오는 건 "화면/테이블"이 아니라 **계정계 조회 API 1개(고객명칭)와 정산 연동 1개**뿐이다.
> 나머지 마감·2차파기·개국합계·전자결재는 **기기/마감 데이터 기반 신규 구현**이다.
